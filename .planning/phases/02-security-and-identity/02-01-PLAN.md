# Plan 02-01: Trusted Identity, Point-of-Access Isolation, Scoped RBAC & Action Confirmation Lifecycle

## Goal
Establish a robust, fail-closed security foundation for Atlas by:
1. Distinguishing trusted production identity from development persona simulation with an explicit fail-closed gate.
2. Enforcing student-level data isolation and department-scoped faculty RBAC at the point of data access (not by natural language regex).
3. Implementing a server-validated cryptographic confirmation lifecycle for high-consequence operations.
4. Adding a clearly demarcated development-only persona simulator in the frontend that is disabled in production.
5. Providing an automated Node 25 native test suite covering all security invariants without adding npm dependencies.

## Architecture & Implementation Specifications

### 1. Security Configuration & Environment Gate (`backend/atlas/security/config.js`)
- Auth mode resolution:
  - `ATLAS_AUTH_MODE`: `'development'` | `'production'`. Defaults to `'production'` if `NODE_ENV === 'production'`, else `'development'`.
  - `ENABLE_DEV_PERSONAS`: Explicit boolean flag (defaults to `true` in development, **strictly forced to `false`** if `ATLAS_AUTH_MODE === 'production'`).
- Production gate:
  - If `ATLAS_AUTH_MODE === 'production'`, client simulation headers (`x-atlas-dev-persona-id`, `x-atlas-user-id`, `x-atlas-role`) are **strictly rejected with HTTP 400 Bad Request**.
  - If no production Identity Provider (IdP) is configured, protected routes fail closed with HTTP 401 (`AUTHENTICATION_REQUIRED`).

- Middleware `extractIdentity(req, res, next)`:

  - **In Development Mode:** Validates `x-atlas-dev-persona-id` against approved test personas. Defaults safely to Alex Kumar with audit log. Sets response header `X-Atlas-Auth-Mode: development-simulation`.
  - Attaches validated `req.user` object to the request.

### 3. Point-of-Access Authorization & Scoped RBAC (`backend/atlas/security/authorization.js`)
- `assertStudentAccess(reqUser, targetStudent)`:
  - **Student Role (`student`):** Strict self-only access (`targetStudent.student_id === reqUser.studentId`). Rejects cross-student access with HTTP 403 Forbidden (`FORBIDDEN_STUDENT_ISOLATION`: `"Access Denied: You do not have permission to access records outside your student account."`). Never leaks target student existence or private metrics.
  - **Faculty Role (`faculty`):** Department-scoped access (`targetStudent.branch === reqUser.department`). If a faculty member queries a student outside their assigned department (e.g. CSE faculty querying an IT student), rejects with HTTP 403 Forbidden (`FORBIDDEN_DEPARTMENT_SCOPE`: `"Access Denied: Record is outside your assigned departmental scope."`).
  - **Admin Role (`admin`):** Institutional audit access across all branches with structured security audit logging.
- `requireRole(allowedRoles)`: Route-level middleware guarding administrative and faculty endpoints.

### 4. Cryptographic Action Confirmation Lifecycle (`backend/atlas/security/confirmation.js`)
- Implements server-side confirmation records with in-memory TTL store (cleaned up automatically):
  - `createConfirmationIntent({ userId, actionType, payload, ttlMs = 300000 })`:
    - Generates cryptographic token: `crypto.randomBytes(32).toString('hex')`.
    - Computes `payloadHash`: `crypto.createHash('sha256').update(JSON.stringify(payload)).digest('hex')`.
    - Binds token to `userId`, `actionType`, `payloadHash`, and `expiresAt` (5 minutes).
    - Returns `{ token, expiresAt, actionType }`.
  - `validateAndConsumeConfirmation({ token, userId, actionType, payload })`:
    - Validates token existence.
    - Validates expiry (`Date.now() <= record.expiresAt`).
    - Validates single-use (`record.consumed === false`).
    - Validates user binding (`record.userId === userId`).
    - Validates payload integrity (`hash(payload) === record.payloadHash`).
    - Sets `record.consumed = true` immediately (replay prevention).
- Action endpoints:
  - `POST /api/atlas/actions/confirm`: Validates token and executes the confirmed action.

### 5. Integration into Agents & Server (`academic.js`, `campus.js`, `communication.js`, `server.js`)
- In `backend/atlas/agents/academic.js`:
  - When query requests a specific student record, pass both `context.user` and `targetStudent` to `assertStudentAccess`.
  - Reject unauthorized access cleanly at the data retrieval point.
- In `backend/atlas/agents/campus.js`:
  - Maintenance ticket filing generates a confirmation intent when `requiresConfirmation` is enabled.
- In `backend/atlas/agents/communication.js`:
  - Campus broadcast circular drafting binds confirmation token to the author's user ID.
- In `backend/server.js`:
  - Mount `extractIdentity` globally on `/api/*`.
  - In `/api/chat` and `/api/atlas/orchestrate`: pass dynamic `req.user` directly to orchestrator.

### 6. Frontend Dev Simulator UI (`SettingsView.jsx`, `ChatArea.jsx`)
- In `SettingsView.jsx`:
  - Display "Campus Identity & Persona Simulator" card ONLY when running in development mode (`import.meta.env.DEV`).
  - Render prominent warning banner:
    `⚠️ DEVELOPMENT TEST SIMULATOR ONLY · NOT FOR PRODUCTION`
    `Simulated personas are strictly restricted to local development testing and are rejected in production environments.`
  - Persona selection dispatches `'x-atlas-dev-persona-id'` header via `ChatArea.jsx`.
  - In production mode, the simulator is completely omitted from the DOM.

## must_haves

### truths
- Production mode strictly rejects client-supplied simulation headers and fails closed if unauthenticated.
- Student-level data isolation is enforced at the data accessor layer: students can NEVER view other students' private records.
- Faculty permissions are strictly bounded by assigned department scope.
- Consequential actions require single-use, cryptographically bound confirmation tokens.
- Development persona simulation is explicitly quarantined, labeled, and disabled in production.
- Existing AGENTX runtime capabilities, SSE chat streaming, history, integrations, and background tasks remain 100% functional.
- All security guarantees are verified by automated `node:test` tests.

### prohibitions
- No trusting `x-atlas-user-id` in production.
- No relying solely on natural language regex to enforce authorization.
- No leaking private student data or existence in 403 error responses.
- No claiming production-grade authentication when operating in development simulation mode.
- No new npm dependencies added (use Node.js built-in `node:test`, `node:assert`, and `node:crypto`).
