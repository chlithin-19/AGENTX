# Plan 02-01: Trusted Identity, Point-of-Access Isolation, Scoped RBAC & Hardened Confirmation Lifecycle

## Goal
Establish a robust, fail-closed security foundation for Atlas by:
1. Rejecting unsafe production configuration at startup and enforcing that development personas are unconditionally disabled when `NODE_ENV=production`.
2. Implementing verified identity validation in production and a strictly quarantined simulation mode in non-production environments.
3. Enforcing student-level data isolation and department-scoped faculty RBAC at the point of data access (not by natural language regex).
4. Implementing a hardened cryptographic confirmation lifecycle that executes stored server-side proposals with atomic single-use replay prevention.
5. Providing an automated Node 25 native test suite covering all security invariants, configuration conflicts, and concurrent execution attacks.

## Architecture & Implementation Specifications

### 1. Security Configuration & Startup Gate (`backend/atlas/security/config.js`)
- Validates environment configuration at startup:
  - If `NODE_ENV === 'production'`, `enableDevPersonas` is strictly `false`. If an environment attempts to set `ENABLE_DEV_PERSONAS=true` while `NODE_ENV=production`, startup throws `SecurityConfigurationError('Unsafe configuration: Development personas cannot be enabled in production environments.')`.
  - Determines `authMode`: `'production'` (when `NODE_ENV === 'production'` or `ATLAS_AUTH_MODE === 'production'`) vs `'development'`.
  - Exports validated `AUTH_CONFIG`.

- Middleware `extractIdentity(req, res, next)`:
  - **In Production Mode:**
    - Rejects requests containing development simulation headers (`x-atlas-dev-persona-id`, `x-atlas-user-id`, `x-atlas-role`) with HTTP 400 Bad Request.
    - Validates cryptographic Bearer token or server-verified session cookie using configured institutional secret.
    - If no institutional token verifier or valid token is present, fails closed with HTTP 401 (`AUTHENTICATION_REQUIRED`). Never claims to be production-authenticated without verified credentials.
  - **In Development Mode:**
    - Validates `x-atlas-dev-persona-id` against approved test personas. Defaults safely to Alex Kumar with audit log.
    - Emits response header `X-Atlas-Auth-Mode: development-simulation`.
    - Attaches validated `req.user` object to the request.

### 3. Point-of-Access Authorization & Scoped RBAC (`backend/atlas/security/authorization.js`)
- `assertStudentAccess(reqUser, targetStudent)`:
  - **Student Role (`student`):** Strict self-only access (`targetStudent.student_id === reqUser.studentId`). Rejects cross-student access with HTTP 403 Forbidden (`FORBIDDEN_STUDENT_ISOLATION`: `"Access Denied: You do not have permission to access records outside your student account."`). Never leaks target student existence or private metrics.
  - **Faculty Role (`faculty`):** Department-scoped access (`targetStudent.branch === reqUser.department`). If a faculty member queries a student outside their assigned department (e.g. CSE faculty querying an IT student), rejects with HTTP 403 Forbidden (`FORBIDDEN_DEPARTMENT_SCOPE`: `"Access Denied: Record is outside your assigned departmental scope."`).
  - **Admin Role (`admin`):** Institutional audit access across all branches with structured security audit logging.
- `requireRole(allowedRoles)`: Route-level middleware guarding administrative and faculty endpoints.

### 4. Hardened Cryptographic Confirmation Lifecycle (`backend/atlas/security/confirmation.js`)
- Stored Server-Side Proposal Lifecycle:
  - `createConfirmationIntent({ userId, actionType, proposal, ttlMs = 300000 })`:
    - Validates allowlisted action type (`campus.create_maintenance_ticket`, `communication.draft_broadcast`).
    - Generates cryptographic token: `crypto.randomBytes(32).toString('hex')`.
    - Stores the exact normalized server-side `storedProposal`.
    - Computes `payloadHash` of the proposal.
    - Sets `expiresAt` (5 minutes) and `consumed = false`.
    - Returns `{ confirmationToken: token, expiresAt, actionType }`.
  - `executeConfirmedAction({ token, reqUser })`:
    - Looks up token in atomic registry.
    - Rejects if token missing -> 404 Not Found.
    - Rejects if token expired -> 410 Gone.
    - Rejects if user ID mismatch (`record.userId !== reqUser.id`) -> 403 Forbidden.
    - **Atomic Consumption:** Checks `if (record.consumed) throw ConflictError('Confirmation token already consumed.')` and immediately sets `record.consumed = true` before dispatching side-effects to prevent concurrent race-condition replays.
    - Re-validates user authorization for the action type.
    - **Executes the storedProposal**, ignoring any client-supplied arguments.
    - Returns execution result.
- Action endpoint:
  - `POST /api/atlas/actions/confirm`: Receives `{ confirmationToken }` and calls `executeConfirmedAction`.

### 5. Integration into Agents & Server (`academic.js`, `campus.js`, `communication.js`, `server.js`)
- In `backend/atlas/agents/academic.js`:
  - Enforce `assertStudentAccess` at every data accessor (`get_attendance`, `get_cgpa`, `get_backlogs`, etc.).
  - Rejects unauthorized access cleanly at the data retrieval point.
- In `backend/atlas/agents/campus.js` & `communication.js`:
  - When consequential action is triggered, generate a confirmation intent and store the proposal.
- In `backend/server.js`:
  - Validate security configuration at startup.
  - Mount `extractIdentity` globally on `/api/*`.
  - In `/api/chat` and `/api/atlas/orchestrate`: pass dynamic `req.user` directly to orchestrator.

### 6. Frontend Dev Simulator UI (`SettingsView.jsx`, `ChatArea.jsx`)
- In `SettingsView.jsx`:
  - Render "Campus Identity & Persona Simulator" card ONLY when running in development mode (`import.meta.env.DEV`).
  - Render prominent warning banner:
    `⚠️ DEVELOPMENT TEST SIMULATOR ONLY · NOT FOR PRODUCTION`
    `Simulated personas are strictly restricted to local development testing and are rejected in production environments.`
  - Persona selection dispatches `'x-atlas-dev-persona-id'` header via `ChatArea.jsx`.
  - In production mode, the simulator is completely omitted from the DOM.

## must_haves

### truths
- Production mode strictly rejects client-supplied simulation headers and fails closed if unauthenticated.
- Unsafe startup configuration (e.g. `NODE_ENV=production` + `ENABLE_DEV_PERSONAS=true`) is rejected at startup.
- Student-level data isolation is enforced at the data accessor layer: students can NEVER view other students' private records.
- Faculty permissions are strictly bounded by assigned department scope.
- Consequential actions execute stored server proposals with atomic single-use replay prevention.
- Development persona simulation is explicitly quarantined, labeled, and disabled in production.
- Existing AGENTX runtime capabilities, SSE chat streaming, history, integrations, and background tasks remain 100% functional.
- All security guarantees are verified by automated `node:test` tests.

### prohibitions
- No trusting `x-atlas-user-id` in production.
- No relying solely on natural language regex to enforce authorization.
- No leaking private student data or existence in 403 error responses.
- No accepting arbitrary client-supplied arguments when confirming actions.
- No claiming production-grade authentication when operating in development simulation mode.
- No new npm dependencies added (use Node.js built-in `node:test`, `node:assert`, and `node:crypto`).

- Run `npm --prefix backend test` -> all security test assertions pass cleanly.
